# 实现原理

> 车机应用商店第三方 APK 注入方案 —— 技术原理说明
>
> **适用边界**：本方案仅用于**本人拥有**的车机与本人设备，在**自建热点**网络内完成。
> 所用中间证书已被 Chrome / Firefox / Apple / Microsoft 于 2026-10 移除并吊销，
> 现代系统无法被此链欺骗；有效性只针对**未更新信任库的旧车机**。

---

## 一、总体思路

车机（Android）打开应用商店时，链路是：

```
车机 ──Wi-Fi──> 笔记本热点(192.168.137.1)
                    ├─ DNS: 把商店域名解析到 192.168.137.1   ← hosts 劫持
                    └─ TLS: 代理出示"受信任"证书完成握手        ← 伪造中间证书签的叶子证书
                          └─ HTTP: 改写详情 JSON + 直接下发本地 APK
```

三个环节各自解决一个难题：

| 环节 | 要解决的问题 | 手段 |
|---|---|---|
| DNS 劫持 | 车机怎么把请求发到笔记本 | hosts 文件 + 热点 ICS DNS 代理遵守 hosts |
| TLS 冒充 | 车机凭什么相信你不是商店服务器 | 还原 eMudhra 弱私钥中间证书，签发叶子证书 |
| 内容替换 | 详情页显示谁、下载谁 | 改写详情 JSON；拦截下载路径直投本地 APK |

## 二、DNS 劫持：让车机找上门

### 2.1 车机的 DNS 从哪来

Windows 开移动热点后，ICS（Internet Connection Sharing）会：

- 给车机分配 `192.168.137.x` 地址
- 把 `192.168.137.1`（笔记本）同时作为**网关**和 **DNS 服务器**下发

于是车机对 `prod-r-platform.z-onesoft.com` 的解析请求会发到笔记本的 53 端口。

### 2.2 ICS DNS 代理会遵守 hosts

Windows 的 ICS DNS 代理（`SharedAccess` 服务）在解析客户端查询时，
**会先查本机 hosts 文件**。因此只要在 hosts 里写：

```
192.168.137.1 prod-r-platform.z-onesoft.com
192.168.137.1 prod-dp-public-es33.oss-cn-shanghai.aliyuncs.com
```

车机解析这两个域名就会得到 `192.168.137.1`，直接连到笔记本。

> **实测验证**：向 `192.168.137.1:53` 发一个 A 查询，返回 `192.168.137.1`。
> 这一步是整个方案的前提，务必在目标机器上实测（见操作指南第 3 步）。

### 2.3 回源必须自建 DNS（防死循环）

hosts 劫持之后，**笔记本自己**解析这两个域名也会得到 `192.168.137.1`。
如果代理用系统解析器去回源，就会解析到自己 → 无限回环。

因此代理内置了一个最小 DNS 客户端：

```
自建 UDP 查询 → 223.5.5.5 → 拿到真实 IP → 直连真实 IP:443
```

（`proxy_server.py` 的 `dns_resolve()`）

## 三、TLS 冒充：让车机相信这个证书

### 3.1 问题

车机是 Android，校验服务端证书链时要求链能接到**它系统信任库里的某个公共根 CA**。
我们没有商店的私钥，无法签发合法证书 —— 除非……

### 3.2 eMudhra 的密钥生成事故

2025-04-30，eMudhra 在一次密钥生成仪式（KGC）中，HSM 脚本的一个缺陷导致
**额外生成了一组弱密钥**，并因密钥标签相似而**误用这组弱密钥**去生成 CSR、
交给根 CA 签名。这组弱密钥被发布到了各浏览器根库。

后果：8 张 intermediate CA 证书的私钥 d **小于 256**（正常 P-384 应有约 384 位熵）。
任何人拿到公开证书，都能在毫秒级内还原私钥，从而签发任意域名的可信证书。

受影响证书（`certs/impacted-intermediates.json` 有完整指纹）：

| 证书 | 用途 | 私钥 d |
|---|---|---|
| EM DV TLS CA - G3B | TLS (DV) | 156 |
| EM OV TLS CA - G3B | TLS (OV) | 155 |
| EM EV TLS CA - G3B | TLS (EV) | 115 |
| EM DV TLS CA - G3C | TLS (DV) | 230 |
| **EM OV TLS CA - G3C** | TLS (OV) | **4** |
| EM EV TLS CA - G3C | TLS (EV) | 56 |
| EM OV CS CA - G3B | 代码签名 | 66 |
| EM OV CS CA - G3C | 代码签名 | 237 |

### 3.3 还原私钥（`certs/recover_keys.py`）

ECDSA 签名基于椭圆曲线点乘。公钥是 `Q = d·G`（G 为 P-384 基点，d 为私钥）。
既然 d 极小，穷举即可：

```
对 d = 1 .. 2^20:
    计算 d·G 的坐标 (x, y)
    若 (x, y) == 证书 SPKI 里的公钥坐标 → 命中
```

实现要点（`recover_keys.py`）：

1. **纯 Python 雅可比坐标**做点乘，避免逐次模逆
2. **增量加法**：`d·G` 逐个累加 `G`，每次只做一次点加
3. **先自检**：用 `cryptography` 派生 d=1,2,3,7,12345 的公钥，与本地实现比对，
   确认数学实现正确后再跑枚举
4. **二次交叉校验**：还原出的 d 重新派生公钥，与证书坐标逐位比对

结果：16 张证书副本 / 8 个独立 SPKI **全部命中，交叉校验全部通过**。
私钥只落盘在 `certs/keys/`（PKCS8），不打印到任何输出。

### 3.4 签发叶子证书（`certs/sign_leaf.py`）

用还原出的中间证书私钥，签一张叶子证书：

- **Subject / Issuer**：`CN=prod-r-platform.z-onesoft.com`（issuer 必须是中间证书的 subject）
- **SAN**：`prod-r-platform.z-onesoft.com` + `prod-dp-public-es33.oss-cn-shanghai.aliyuncs.com`
- **有效期**：**从一年前起算两年**（`notBefore = now - 365d`，`notAfter = now + 365d`）
  —— 车机系统时钟常常不准，±1 年的窗口保证任何合理偏差都能通过
- **扩展**：`basicConstraints=CA:FALSE`、`keyUsage=digitalSignature+keyEncipherment`、
  `extendedKeyUsage=serverAuth`、`SAN`、`SKI`、`AKI`
- **签名算法**：`ecdsa-with-SHA384`（与中间证书一致）
- **叶子密钥**：RSA 2048（老车机 TLS 栈兼容性最好）

### 3.5 信任路径的选择（踩过的坑）

8 张中间证书各有**两个副本**：

- `EM OV TLS CA - G3C`，issuer = `AAA Certificate Services`（Comodo 老根）
- `EM OV TLS CA - G3C`，issuer = `emSign Root TLS CA - G3`

**两者的 subject 完全相同**，这带来一个反直觉的问题：

| 下发内容 | OpenSSL/Python | JSSE / Android Conscrypt |
|---|---|---|
| 只发 AAA 版 | 只通 AAA 根 | 只通 AAA 根 |
| 只发 emSign 版 | 只通 emSign 根 | 只通 emSign 根 |
| 两版同发 | **只通 AAA 根**（选错分支） | **两族根都通**（会回溯） |
| **AAA 版 + emSign 版 + 交叉签名根** | — | **3/3 全通** ✅ |

最终 `chain.pem` = 4 张：

```
[0] leaf                                   (SAN 两个域名)
[1] EM OV TLS CA - G3C  (issuer=AAA Certificate Services)
[2] EM OV TLS CA - G3C  (issuer=emSign Root TLS CA - G3)
[3] emSign Root TLS CA - G3  (issuer=emSign ECC Root CA - G3)   ← 交叉签名, 使第 4 族根可达
```

**第 3 张不能省**：它是交叉签名版（issuer 不是自己），既能让
`emSign ECC Root CA - G3`（四家根库都有）可达，又不会造成路径歧义。

> 验证工具：`certs/verify_jsse.py` 用 JDK 17 的 JSSE TrustManager 做**真实握手**，
> 分别以三个候选根作唯一信任锚 —— JSSE 的路径构建逻辑与 Android Conscrypt 最接近。
> `certs/jsse_matrix_test.py` 是穷举链组合的矩阵测试工具。

## 四、内容替换：改写详情 + 直投 APK

### 4.1 serve 规则 —— 直接下发本地 APK

车机点"安装"时，下载器（UA=`OkDownload/1.0.7`）请求：

```
GET https://prod-dp-public-es33.oss-cn-shanghai.aliyuncs.com/ecology/ecofile-<hash>.apk
```

代理命中 serve 规则后**不回源**，直接返回本地 APK：

- 支持 `Range` / `206` / `416` / `Content-Length` / `Accept-Ranges` / `Content-Range`
- **256KB 分块读，4MB 批量发送**（大文件必须；逐块 sendall 会因 TLS 记录开销
  把 150MB 拖到 195 秒，批量后 0.97 秒）
- 每 10% 打一条进度日志

> **踩过的坑**：最初按任务描述写成只匹配 `.1` 后缀，但车机实际下载的是
> `/ecology/ecofile-<hash>.apk`。规则改为按前缀 `/ecology/` 匹配后立即命中。

### 4.2 patch 规则 —— 改写详情 JSON

车机进详情页时 POST：

```
POST https://prod-r-platform.z-onesoft.com/eco/ippf/appMarket/vehicle/app/detail
```

代理**正常回源**，把响应 JSON 按点路径改字段后重新序列化：

```json
{
  "data": {
    "appName":        "最美天气"      → 你的应用名
    "appPackage":     "com.icoolme..." → 你的包名
    "appActualSize":  "7077"           → 你的字节数 // 1024
    "appDisplaySize": "6M"             → 你的字节数 // 1048576 + "M"
  }
}
```

体积换算公式（`appActualSize` 单位 KB）：

```
appActualSize  = 字节数 // 1024          例: 157605849 → "153911"
appDisplaySize = 字节数 // 1048576 + "M"  例: 157605849 → "150M"
```

处理响应时的三个关键点：

1. **必须先解 chunked**
   真实详情接口返回 `Transfer-Encoding: chunked`，body 形如
   `68d\r\n{"code":200,...}\r\n0\r\n\r\n`。不解就把 chunk 长度 `68d`
   当成 JSON 内容 → `Extra data: line 1 column 3 (char 2)` → patch 永远不生效。
2. **删除旧 `Content-Length` / `Content-Encoding` / `Transfer-Encoding`**，
   写入新的 `Content-Length`（否则客户端按旧长度读，会解析失败或卡住）
3. **一个字段都没命中就原样转发**（不破坏原响应）

### 4.3 字段结构（来自真实响应 dump）

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "appResourceUri": "https://prod-dp-public-es33.oss-cn-shanghai.aliyuncs.com/ecology/ecofile-f2382ade....apk",
    "appPackage": "com.icoolme.car.weather",
    "appName": "最美天气",
    "appActualSize": "7077",
    "appDisplaySize": "6M",
    ...
  }
}
```

`appResourceUri` **不需要改** —— 它指向的路径会被 serve 规则按 `/ecology/` 前缀拦截，
自动换成你的 APK。

## 五、代理服务器架构（`proxy_server.py`）

### 5.1 TLS 层

```python
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain(certfile="pki/chain.pem", keyfile="pki/leaf.key.pem")
ctx.set_alpn_protocols(["http/1.1"])       # 只声明 HTTP/1.1
```

**单 SSLContext，绝不按 SNI 切换** —— 切换会导致握手失败
（ClientHello 阶段就要选定证书，同一 socket 无法二次握手）。

### 5.2 请求处理流程

```
TLS 握手
  ↓
读请求行 + 头 + body(支持 Content-Length 与 chunked)
  ↓
Host 判定 → 规则匹配
  ├─ 命中 serve → 不回源, 直投本地 APK
  ├─ 命中 patch → 回源 → 解 chunked → 改 JSON → 重写头 → 返回
  └─ 其余      → 原样转发 (字节级透传)
```

### 5.3 回源的三个坑

| 坑 | 现象 | 修法 |
|---|---|---|
| 上游 `Connection: keep-alive` | 一直读到 EOF → 等到 socket 超时 → 响应发不回车机 → 应用商店转圈 | 按 `Content-Length`/chunked **精确读取，读够即停** |
| 透传 keep-alive 给车机 | 车机复用我方已关闭的连接 → 下个请求失败 | 统一改写 `Connection: close` |
| `return` 与 `sendall` 粘在一行 | 日志显示"原样转发 1739 bytes"正常，**实际响应从未发出** → 车机报「网络异常」 | 分行；并加"响应完整性"回归测试 |

## 六、验证体系

| 工具 | 作用 | 关键用例 |
|---|---|---|
| `selftest.py` | 61 项自检 | serve/Range/416、patch 逻辑、体积换算、**响应完整性**、**车机真实下载路径**、**真实 chunked 响应回归** |
| `certs/verify_jsse.py` | JSSE 真实握手 | 3 个候选信任根各握手一次，要求 3/3 |
| `certs/e2e_patch_test.py` | patch 全链路 | 本地模拟上游（明文 + gzip），验证改写与头重写 |
| `certs/jsse_matrix_test.py` | 链组合矩阵 | 穷举 chain.pem 组成 × 信任库组合，找最佳 |
| `certs/recover_keys.py` | 私钥还原 | 纯 Python 雅可比 P-384 枚举 |
| `certs/sign_leaf.py` | 叶子签发 | 有效期从一年前起算两年 |

### 回归测试的由来

`certs/fixtures/real_detail_chunked.bin` 是**从车机真实请求中 dump 下来的上游原始响应**
（`PROXY_DUMP=1` 环境变量落盘）。它锁定了"必须解 chunked"这个行为 ——
没有这个固件，任何改动破坏 chunked 解析都不会被发现。

> **教训**：本机测试用的是**无效签名头**，上游返回的是 208 字节错误 JSON（明文），
> 与真实详情响应（chunked + 完整对象）结构完全不同。
> 验证"对真实接口的改写"必须用真实数据固件，不能靠本机伪造请求。

## 八、安全边界

1. **仅限本人设备**：全部操作只在本人笔记本与本人车辆上完成。
2. **证书已失效**：所用 intermediate 于 2026-10-18 被 eMudhra 以 `caCompromise`
   撤销，并被 Chrome / Firefox / Apple / Microsoft 移除。**现代系统无法被此链欺骗**，
   有效性只针对未更新信任库的旧车机。
3. **私钥只落盘**：`certs/keys/*.key.pem`、`pki/leaf.key.pem`，
   从不打印到对话或日志。
4. **证书链不完整会失败**：`certs/verify_jsse.py` 3/3 通过是上车的必要条件。
5. **还原 hosts**：`hosts.workbuddy.bak` 备份，`setup.ps1 -Restore` 一键还原。
